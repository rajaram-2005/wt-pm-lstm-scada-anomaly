# WT-PM model 13 — architecture

**Model:** LSTM sequence anomaly detection on wind-turbine SCADA
**Position in the fabric:** Layer 4 (anomaly intelligence) with interfaces up to
Layers 6, 12 and 13.

This document describes what is actually implemented, why each piece exists, and
where the boundary of the claim is. Numbers quoted here come from the reference
run (`wtpm demo`, 60 days, 30 epochs, two ensemble members, stride 2) and are
regenerated by every run report.

---

## 1. Where this model sits

The WT-PM research ecosystem is a 25-model collection spanning vibration
intelligence, SCADA analytics, anomaly detection, fault classification, RUL
prognostics, physics-guided learning, digital twins, graph learning, explainable
AI, and edge deployment. Model 13 is the *SCADA sequence* branch: it consumes
multi-channel ten-minute SCADA records and emits timestamped anomaly records.

The value of the collection is not that it contains 25 models; it is that the
models can be composed. Composition needs interfaces, and this repository takes
a position on each of them:

| Interface | Here |
| --- | --- |
| common data schema | `wt_pm_lstm.schema` — 12 canonical channels, quality codes, versioned |
| shared feature representation | per-channel robust standardisation; windowed sequences |
| model registry | `wt_pm_lstm.registry` — `.npz` weights + JSON sidecar, config fingerprint |
| experiment tracking | `runs/<name>-<fingerprint>/` with config, metrics, history, alerts |
| evaluation protocol | `wt_pm_lstm.evaluate` + `docs/fidelity_ladder.md` |
| uncertainty propagation | ensemble disagreement per window, carried into each record |
| drift detection | `wt_pm_lstm.drift` — PSI + Page-Hinkley, reported in every run |
| common inference API | `wt_pm_lstm.api` — `POST /score`, `GET /schema`, `GET /health` |

## 2. Data contract (`schema.py`)

Twelve channels at ten-minute resolution, in Unix seconds:

* **exogenous (3):** `wind_speed_ms`, `ambient_temp_c`, `grid_frequency_hz`
* **control (1):** `pitch_angle_deg` — observed, handed to the decoder, never scored
* **machine responses (8):** rotor speed, yaw error, power, main-shaft torque,
  generator current, nacelle temperature, gearbox oil temperature, bearing
  vibration RMS

Three decisions in this contract are load-bearing:

1. **Missing data is never imputed with a sentinel.** A missing sample is
   `mask=False` plus a quality code. A `-999` would flow into the scaler, the
   loss and the residuals, and would eventually be learned as a real state.
2. **Out-of-range values are kept and flagged.** A 20 MW power reading is
   evidence; deleting it hides a sensor fault. `validate(strict_bounds=True)`
   reports it for callers that need the stricter check.
3. **Channels have roles.** Exogenous channels describe the weather. Scoring
   their residuals measures the wind forecast, not the turbine — the first
   version of this detector scored all twelve channels and reached ROC 0.516,
   i.e. chance. Restricting scoring to the eight response channels is the single
   most important modelling decision in the repository (ROC 0.748 → 0.77).

## 3. Model (`nn.py`)

A NumPy sequence autoencoder: an LSTM (or GRU) encoder over a 36-sample (6 h)
window, a linear projection to a latent vector, and a decoder that reconstructs
the window and forecasts the next step. Two heads share one latent:

* **reconstruction** — is this window an out-of-distribution *state*?
* **forecast** — does the next step follow the *dynamics*?

The decoder receives the latent vector *and* the exogenous channels at every
step. This is the physics-AI coupling in its minimal honest form: the turbine's
response is modelled conditional on the conditions it operated in, so the model
is not asked to predict the weather.

Forward and backward passes are hand-written. Every gradient is verified against
a central finite difference of the training loss (`tests/test_nn.py`); a sign
error in an LSTM gate produces a model that trains, scores, and is quietly
worse, which is why this is the most heavily tested module.

## 4. Normal-behaviour model (`baseline.py`)

A ridge regression on a degree-2 expansion of the context channels predicts
each response channel. R² on the reference run: rotor speed 0.97, torque 0.96,
generator current 0.95, power 0.94, nacelle 0.90, vibration 0.89, gearbox oil
0.82, yaw error 0.03 (yaw error is not condition-driven — that is expected, not
a defect).

The NBM exists because of a structural blind spot: **reconstruction and forecast
residuals cannot see a slow, smooth fault.** A gearbox oil cooler that fouls
over two days raises the oil temperature by 10 °C; the new level is *easy* to
reconstruct and *easy* to forecast. Adding capacity or training longer does not
help — it makes the model better at reproducing the fault. The NBM asks a
different question ("what should this channel be, given the conditions?") and is
the only *absolute* component of the score.

## 5. Detection (`detect.py`)

Four per-channel components are fused with configurable weights, reduced to one
score per timestep, smoothed, and passed to a hysteresis alarm counter.

| component | weight | sees |
| --- | --- | --- |
| `reconstruction` | 0.30 | out-of-distribution states |
| `temporal` | 0.20 | violations of the dynamics |
| `trend` | 0.20 | slow level shifts (trailing mean of the signed residual) |
| `level` | 0.30 | absolute deviation from the expected value |

Three implementation decisions matter:

* **Fusion is per channel, reduction is last.** Averaging eight channels first
  dilutes a single-channel fault: a gearbox-oil level 3.3 σ high contributes 1.4
  once averaged over the other seven, and the fault disappears. The default
  reduction is `max` (worst channel wins); `topk` and `mean` are available, and
  the difference is measured, not assumed (F1 0.595 / 0.578 / 0.506 at the time
  the choice was made).
* **The trend statistic is causal and per channel.** A centred window would be
  marginally smoother and impossible to reproduce online.
* **Sensors fail too, and differently.** A stuck channel has *zero* temporal
  residual, which every value-based score rewards. A separate rule raises a
  sensor-health alarm when a scored channel does not change for 18 consecutive
  samples; those records name the channel and recommend a sensor check rather
  than a mechanical inspection. Exact constancy is used rather than a variance
  threshold because legitimately quiet channels exist — rotor speed is constant
  at rated in region 3, and a variance rule fired on every one of them.

### The threshold is a budget, not a quantile

The alarm threshold is the quantile of the calibration score implied by
`target_false_alarm_minutes_per_day` (default: ten minutes per day, i.e. one
sample). This is an explicit statement about how much alarm time a crew is
willing to spend on healthy machines — the same kind of statement as an SLO —
and it is monotone in the budget, which is what makes it usable.

An earlier attempt calibrated on the number of alarm *events* instead. That is
not monotone: a very low threshold puts the score permanently above it, which is
*one* long event, not many. Bisection on a non-monotone objective returned a
threshold in the middle of the score distribution and produced 68 alarm samples
per day. `tests/test_detect.py` pins that trap.

Alarm time and false-alarm time are reported separately, and the false-alarm
rate excludes the hysteresis tail after a genuine detection — the policy
*requires* the alarm to persist there, so counting it would charge every
detection twice.

## 6. Evaluation (`evaluate.py`, `docs/fidelity_ladder.md`)

Raw point-wise precision/recall/F1 are the headline, with a 95 % confidence
interval from a moving-block bootstrap (below one day, blocks preserve the
autocorrelation that an i.i.d. bootstrap destroys; single-day resolution is
reported as unresolved). Point-adjusted metrics are computed and reported as
secondary, with the caveat, because they appear throughout the SCADA literature
and refusing to publish them invites incomparable claims.

Reported alongside: PR-AUC and ROC-AUC (threshold-free), event recall and
median detection latency in samples, false-alarm time per day, total alarm time
per day, per-family recall, and an operating-point table. The table uses
test-band labels, so it is labelled in the report as **evidence, not a selection
procedure**.

## 7. Drift (`drift.py`)

PSI per channel (0.1 watch, 0.25 act) plus Page-Hinkley change points on the
score stream. The monitor fires on essentially every multi-week synthetic run.
That is worth stating plainly rather than tuning away: a nine-day calibration
window does not represent a sixty-day operating period, so the budget estimated
on calibration is exceeded on the monitoring band. The detector is not
necessarily unstable — the *threshold transfer* is the problem, and the drift
section exists to say so.

## 8. Serving (`api.py`, `cli.py`, `report.py`)

`wtpm serve` exposes the contract over HTTP with the standard library only:
`POST /score` (JSON samples in, anomaly records out), `GET /schema`,
`GET /health`, and `GET /sample` (simulator batches, so the contract can be
exercised end to end without a real SCADA export).

Two details make the API trustworthy rather than merely working:

* **Requests are validated against the schema.** Unknown channels, missing
  channels and too-short batches are rejected with 400 and a reason.
* **Cold starts cannot raise alarms.** The causal window statistics and the EWMA
  are undefined for the first samples of a batch, and the head of a batch scored
  15.4 against a threshold of 11.4 while decaying to 3.3 over 200 samples — so a
  backfill or a single-shot API call used to alarm in its first hour. Alarms are
  now suppressed for `max(window, trend_window)` samples while the samples
  themselves are still scored, and `GET /sample` returns the *tail* of a longer
  record so a demonstration batch carries real causal history. Requests are validated
against the schema: unknown channels, missing channels and too-short batches are
rejected with 400 and a reason, because a silent default for a physical
measurement is worse than an error.

Every run also writes `REPORT.md`, a run record under `runs/<name>-<fingerprint>/`
and a loadable bundle (`.npz` + `.json`). The bundle round-trips exactly, and
`tests/test_pipeline.py` asserts it: a bundle that scores differently from the
object it came from is a reproducibility failure that no metric would reveal.

## 9. Known limits

* **Simulated data.** The physics is explicit and the labels are exact, but
  simulated faults are cleaner than field faults; absolute metric values are not
  transferable to a real asset without re-calibration.
* **Three of seven fault families are missed** in the reference run
  (`converter_fault`, `sensor_drift`, and `gearbox_thermal` is detected in
  samples but late relative to the 6 h tolerance). The NBM sees them at only
  ~0.93–1.06 mean |z| against 0.685 healthy, so they are marginal by
  construction, not by tuning.
* **One threshold for all conditions.** Operating-point-dependent thresholds are
  future work.
* **Hardware is not in scope.** Nothing here runs on a controller; the edge
  deployment path belongs to the TinyML/ESP32 repositories.
